## Architecture

PyEDB is a Python API for Ansys Electronics Database (EDB/AEDB) layout design automation. It has a **dual-backend** architecture:

- **`src/pyedb/grpc/`** — Primary backend using gRPC (`ansys-edb-core`) for remote/cross-platform access
- **`src/pyedb/dotnet/`** — **Deprecated** legacy backend using .NET/pythonnet (`ansys-pythonnet`). Do not add new features here.
- **`src/pyedb/configuration/`** — JSON/Pydantic-based configuration system (`cfg_*.py` files) for declarative design setup

Entry point: `from pyedb import Edb`. Backend selection via the `grpc` parameter (`True`/`False`/omitted).
When `grpc` is omitted, the backend is selected automatically from the resolved AEDT version: gRPC for
Ansys release 2026.1 and later, DotNet for Ansys release 2025.2 and earlier. Both backends expose the
same high-level API surface.

**Canonical compatibility reference:** do not restate backend-default, minimum-AEDT-version, or
optional-dependency rules from memory — they have drifted out of sync across pages before. Always
check `doc/source/getting_started/backend_compatibility_migration.rst` (published as
"Backend, compatibility, and migration") and the `_use_grpc_by_default()` logic in
`src/pyedb/generic/design_types.py` as the source of truth.

**`llms.txt`:** a curated, agent-facing documentation map lives at the repository root (`llms.txt`).
It lists canonical pages (quick start, object model, backend compatibility, user guide, configuration,
workflows, examples) and repeats the highest-risk rules (backend default, `version` vs `edbversion`,
non-destructive save semantics). Prefer it over guessing which `.rst` page is authoritative.

## Project Layout

```
src/pyedb/          # Main package (version from __init__.py via flit)
  dotnet/edb.py     # Legacy Edb class (dotnet backend)
  grpc/edb.py       # gRPC Edb class
  configuration/    # Pydantic models for JSON-driven configuration (cfg_*.py)
  common/           # Shared utilities across backends
  generic/          # Generic helpers
tests/
  unit/             # Fast tests, no license needed (marker: @pytest.mark.unit)
  integration/      # Require EDB/AEDT license (marker: @pytest.mark.integration)
  system/           # Full system tests (marker: @pytest.mark.system)
  example_models/   # Test fixture .aedb projects and data
```

## Development Commands

```bash
pip install -e ".[tests,all]"       # Editable install with test + optional deps
```

## Documentation Commands

```bash
cd doc
make html                           # Build HTML docs into doc/_build/html
sphinx-build -b html source _build/html -w build_errors.txt   # Build and capture warnings to a file
```

- Source lives under `doc/source/`. `doc/source/autoapi/` is generated by AutoAPI at build time —
  do not hand-edit it.
- `_autosummary/` directories under `doc/source/**` are generated by `sphinx.ext.autosummary` and are
  gitignored. Delete them (`find doc -type d -name "_autosummary" -exec rm -rf {} +`) before a from-scratch
  build if you suspect stale stub pages (e.g. after renaming or removing a documented symbol).
- Sphinx caches parsed doctrees (default `doc/_build/<builder>/.doctrees` or a `doctreedir` set in
  `conf.py`/Makefile). After editing a Python docstring, a plain rebuild into a fresh output directory
  can still report stale warnings/errors from the cached doctree. Pass `-E` (or delete the doctree
  cache) to force a full re-read when comparing warning/error counts before and after a docstring
  change, otherwise you may see phantom regressions or miss real fixes.
- Do not assert a Sphinx build is warning/error-free without actually running it; grep the warnings
  file rather than assuming.
- `doc/check_doc_quality.py` runs a clean build and enforces the warning/error ceiling used in CI
  (`doc-quality-gate` job in `.github/workflows/ci-pr.yml`). Run it locally
  (`python doc/check_doc_quality.py`) before claiming a documentation change is regression-free.

## Editing docstrings safely

Several docstrings in this codebase share near-identical boilerplate (for example, many
`SourceExcitation.create_*` methods repeat the exact phrase `"``True`` when successful, ``False``
when failed."` in their `Returns` section). When using a find/replace-style edit, an `oldString`
built only from that generic text can match the wrong method — or match ambiguously in a way that
is not always rejected — silently corrupting a large surrounding block (this has actually happened
during automated docstring cleanup and briefly deleted the `SourceExcitation` class declaration
itself, breaking `from pyedb import Edb` entirely).

- Anchor edits to a unique `oldString` that includes the `def method_name(` signature line, not
  just generic docstring prose.
- After every docstring edit to a large file, immediately run
  `python -c "from pyedb.grpc.edb import Edb"` (or the equivalent import for the module touched)
  to catch accidental structural damage before moving on to the next edit.
- Prefer one edit at a time with a re-verification step over batching many similar-looking edits.


## Conventions & Patterns

- **Build system**: Flit (`flit_core`). Version is dynamic from `__init__.py`.
- **Linting**: Ruff with numpy-style docstrings. Line length 120. Many rules intentionally ignored (see `pyproject.toml [tool.ruff.lint] ignore`).
- **Config models**: `src/pyedb/configuration/cfg_*.py` use Pydantic v2 models. The main orchestrator is `configuration.py`.
- **Test markers**: Use `@pytest.mark.unit`, `@pytest.mark.grpc`, `@pytest.mark.legacy`, `@pytest.mark.no_licence` as appropriate.
- **Platform-specific deps**: `pywin32` on Windows, `cffi` on Linux for .NET interoperability.

## Key Integration Points

- `ansys-edb-core` — gRPC client stubs for EDB server communication
- `ansys-pythonnet` — .NET CLR bridge for legacy dotnet backend
- Pydantic v2 — all configuration/validation models
- `defusedxml`/`xmltodict` — XML parsing for EDB data

## When Modifying Code

- **Prioritize the gRPC backend** (`src/pyedb/grpc/`). New features and bug fixes should target gRPC first.
- The dotnet backend is **deprecated** — avoid adding new functionality there unless explicitly required for maintenance.
- Configuration additions go in a `cfg_*.py` file with a Pydantic model, registered in `configuration.py`.
- Test fixtures (`.aedb` folders) live in `tests/example_models/`.
